# Архитектура Taler

## 1. Назначение документа

Taler — full-stack приложение для учёта личных финансов. Этот документ фиксирует архитектуру и план разработки до начала реализации. Он основан на требованиях из [project_fullstack_app.md](./project_fullstack_app.md), выбранном стеке из [docs/TECH_STACK.md](./docs/TECH_STACK.md) и правилах из [AGENTS.md](./AGENTS.md).

Цель архитектуры — выполнить каждое требование буквально и обеспечить проверяемое доказательство его выполнения через REST API, интерфейс, автоматические тесты, seed-данные, Swagger, Docker Compose и CI.

## 2. Архитектурный стиль

Приложение строится как модульный монолит из трёх основных сервисов:

- React SPA, собираемый Vite и раздаваемый Nginx;
- NestJS REST API с планировщиком фоновых задач;
- PostgreSQL с доступом через Prisma ORM.

Микросервисы, Redis и очередь сообщений не используются: они не требуются для одного демонстрационного экземпляра приложения и увеличили бы стоимость разработки без доказуемой пользы.

~~~mermaid
flowchart LR
    U[Пользователь] -->|HTTPS / HTTP| F[React SPA / Nginx]
    F -->|/api/v1| B[NestJS REST API]
    F -->|/api/docs| S[Swagger UI]
    B --> P[Prisma Client]
    P --> D[(PostgreSQL)]
    J[NestJS Scheduler] --> B
~~~

В Docker Compose Nginx проксирует /api в backend. Это даёт одинаковый origin для frontend и API, упрощает cookie-аутентификацию и устраняет различия между локальным демо и production-подобным запуском.

## 4. Backend

### 4.1. Модули NestJS

- **AuthModule** — регистрация, вход, выход, выпуск и проверка JWT.
- **UsersModule** — профиль, основная валюта и часовой пояс.
- **CategoriesModule** — CRUD и поиск категорий.
- **TransactionsModule** — CRUD, поиск, фильтры и пагинация транзакций.
- **BudgetsModule** — месячные лимиты и расчёт прогресса.
- **RecurringTransactionsModule** — CRUD шаблонов и автосоздание операций.
- **DashboardModule** — агрегаты для статистики и графиков.
- **CsvModule** — атомарный импорт и потоковый экспорт CSV.
- **AuditModule** — неизменяемый журнал операций над транзакциями и бюджетами.
- **PrismaModule** — единственная точка создания и предоставления Prisma Client.
- **HealthModule** — healthcheck для Docker и smoke-проверок.

Контроллеры отвечают только за HTTP-контракт. DTO и pipes выполняют валидацию, сервисы содержат бизнес-правила, Prisma отвечает за сохранение данных. Prisma-модели напрямую через API не возвращаются.

### 4.2. Общие правила API

- Базовый префикс: /api/v1.
- URL ресурсов используют множественное число и kebab-case.
- Создание возвращает 201, чтение и изменение — 200, удаление без тела — 204.
- Некорректный ввод возвращает 400, отсутствие аутентификации — 401, конфликт состояния — 409.
- Отсутствующая и принадлежащая другому пользователю запись возвращает одинаковый 404.
- Неизвестные поля DTO отклоняются глобальным ValidationPipe.
- Денежные значения и курсы передаются строками, валюты — кодами ISO 4217 в верхнем регистре.
- Временные метки передаются в ISO 8601 UTC; финансовая дата — YYYY-MM-DD в часовом поясе пользователя.

Единая форма ошибки:

~~~json
{
  "statusCode": 400,
  "code": "VALIDATION_ERROR",
  "message": "Request validation failed",
  "details": []
}
~~~

Коллекции возвращаются в единой оболочке:

~~~json
{
  "items": [],
  "meta": {
    "page": 1,
    "pageSize": 20,
    "total": 0,
    "totalPages": 0
  }
}
~~~

page и pageSize должны быть положительными; максимальный pageSize равен 100. Сортировка транзакций по умолчанию — transactionDate DESC, id DESC, что обеспечивает детерминированную пагинацию.

### 4.3. Основные маршруты

| Группа | Маршруты и назначение |
|---|---|
| Auth | POST /auth/register, POST /auth/login, POST /auth/logout, GET /auth/me |
| Users | PATCH /users/me для валюты и часового пояса с доменными ограничениями |
| Categories | CRUD /categories, поиск по имени через GET /categories?search= |
| Transactions | CRUD /transactions; список принимает поиск, фильтры, сортировку и пагинацию |
| CSV | POST /transaction-imports, GET /transactions/export |
| Budgets | CRUD /budgets; ответы списка содержат потрачено, процент и признак превышения |
| Recurring | CRUD /recurring-transactions |
| Dashboard | GET /dashboard?months=6 |
| Audit | GET /audit-log с фильтрами и пагинацией |
| Service | GET /health, Swagger UI /api/docs, OpenAPI JSON /api/docs-json |

Все маршруты, кроме регистрации, входа, healthcheck и Swagger UI, защищены JWT. Каждый новый или изменённый endpoint документируется в Swagger и покрывается Supertest-тестом.

AuthModule нормализует email до lowercase, хеширует пароль Argon2 и выпускает короткоживущий JWT с `sub` и `email`. Токен передаётся только через cookie `access_token` с `HttpOnly`, `SameSite=Strict`, `Path=/` и сроком жизни, совпадающим с JWT; в production добавляется `Secure`. JwtAuthGuard проверяет cookie и сохраняет в request только `id` и `email`, которые контроллеры получают через `@CurrentUser`.

Auth и Users никогда не возвращают Prisma-модель пользователя напрямую. Публичный UserResponseDto содержит только `id`, `email`, `displayName`, `baseCurrency`, `timeZone`, `createdAt` и `updatedAt`. PrismaService создаёт единственный типизированный Prisma Client для модулей приложения. Изменение `baseCurrency` выполняется только после проверки отсутствия транзакций пользователя и отклоняется целиком с `409 BASE_CURRENCY_LOCKED`, чтобы остальные поля того же PATCH не применились частично.

## 5. Модель данных

### 5.1. User

- id, email, passwordHash, displayName;
- baseCurrency — основная валюта пользователя;
- timeZone — IANA timezone;
- createdAt, updatedAt.

Email уникален и нормализуется. Пароль хешируется Argon2. Основную валюту можно выбрать при регистрации и изменить только до появления первой транзакции. После этого API возвращает 409 BASE_CURRENCY_LOCKED, поскольку изменение валюты сделало бы исторические курсы неоднозначными.

### 5.2. Category

- id, userId, name, icon, color, type;
- createdAt, updatedAt;
- уникальность (userId, name).

Категория всегда принадлежит пользователю. GET /categories возвращает items и meta с page (по умолчанию 1), pageSize (по умолчанию 20, максимум 100), стабильной сортировкой по имени и id и необязательным поиском search по подстроке имени без учёта регистра. Имя обрезается по краям и уникально внутри пользователя без учёта регистра; это правило поддерживается уникальным индексом PostgreSQL по userId и lower(name). icon — имя Material icon в snake_case, color — шестизначный #RRGGBB, type — INCOME или EXPENSE. Публичный ответ не содержит userId. Отсутствующая или чужая категория возвращает 404. Удаление разрешено только для неиспользуемой категории; при наличии транзакций, бюджетов или повторяющихся правил возвращается 409 CATEGORY_IN_USE.

### 5.3. Transaction

- id, userId, categoryId;
- type: INCOME или EXPENSE;
- amount — исходная сумма NUMERIC;
- currency — валюта исходной суммы;
- exchangeRateToBase — ручной курс к основной валюте в момент создания;
- baseAmount — зафиксированная сумма в основной валюте;
- transactionDate, description;
- recurringTransactionId и scheduledDate для созданных планировщиком операций;
- createdAt, updatedAt.

Курс определяется как количество единиц основной валюты за одну единицу валюты транзакции. Для операции в основной валюте курс обязан быть равен 1. Для другой валюты пользователь вводит положительный курс вручную. baseAmount рассчитывается backend, а не принимается от клиента.

Индексы создаются по (userId, transactionDate, id) и (userId, categoryId, transactionDate). Уникальность (recurringTransactionId, scheduledDate) предотвращает повторное автосоздание одной операции.

### 5.4. Budget

- id, userId, categoryId;
- month — первый день месяца;
- limitAmount — лимит в основной валюте;
- createdAt, updatedAt;
- уникальность (userId, categoryId, month).

Прогресс не хранится: backend суммирует baseAmount расходных транзакций нужной категории за месяц. Ответ включает spentAmount, remainingAmount, progressPercent и isExceeded.

### 5.5. RecurringTransaction

- id, userId, categoryId;
- тип, сумма, валюта, текущий ручной курс и описание шаблона;
- dayOfMonth, startDate, необязательная endDate;
- nextRunAt, isActive, createdAt, updatedAt.

Для дней 29–31 в коротком месяце используется последний календарный день. Пользователь может обновить ручной курс правила до следующего запуска; при создании операции актуальное значение правила копируется в транзакцию.

### 5.6. AuditLog

- id, userId, entityType, entityId, action;
- before и after в PostgreSQL JSONB;
- createdAt.

Журнал поддерживает только чтение. entityId хранится без обязательного внешнего ключа, чтобы запись сохранялась после удаления сущности. Снимки содержат только бизнес-поля, а денежные значения сериализуются строками. Пароли, JWT и другие секреты никогда не попадают в журнал.

## 6. Безопасность и изоляция данных

JWT хранится в cookie с флагами HttpOnly и SameSite=Strict; в production также устанавливается Secure. Frontend не получает доступ к содержимому токена. Swagger UI работает через тот же origin и после вызова endpoint входа может выполнять защищённые запросы.

Идентификатор пользователя берётся только из проверенного JWT. Backend не принимает userId владельца в защищённых request DTO. Каждая операция Prisma ограничивается текущим userId, а ссылки на категории, бюджеты и повторяющиеся правила дополнительно проверяются на принадлежность тому же пользователю.

Для CORS разрешается только явно настроенный origin. Обязательные переменные окружения валидируются при старте. .env не коммитится; актуальный .env.example содержит только имена и безопасные примеры.

## 7. Ключевые бизнес-процессы

### 7.1. Аудит

Создание, изменение или удаление транзакции либо бюджета и соответствующая запись AuditLog выполняются в одной Prisma-транзакции. При ошибке откатываются обе операции. Аудит создаётся также для транзакций, добавленных через CSV и планировщик.

### 7.2. CSV-импорт

1. Papa Parse читает заголовки и несколько строк на frontend.
2. Пользователь сопоставляет колонки с датой, суммой, категорией, описанием, типом, валютой и курсом.
3. Frontend отправляет исходный файл и JSON-маппинг как multipart/form-data.
4. Backend заново разбирает файл через csv-parse, проверяет каждую строку и принадлежность категорий.
5. Импорт атомарный: при любой ошибке ничего не записывается, а ответ содержит номера строк и причины.
6. При успехе транзакции и их audit-записи создаются в одной Prisma-транзакции.

Размер файла и количество строк ограничиваются конфигурацией. Для операции не в основной валюте CSV обязан содержать валюту и курс; для основной валюты backend устанавливает курс 1.

### 7.3. CSV-экспорт

GET /transactions/export принимает те же фильтры, что и список транзакций: даты, категорию, диапазон суммы, тип и поиск по описанию. Пагинация не применяется. Ответ имеет Content-Type: text/csv и Content-Disposition: attachment; выгружаются только данные текущего пользователя.

### 7.4. Повторяющиеся транзакции

Один declarative cron job периодически выбирает активные правила с nextRunAt <= now. Обработчик также выполняется при старте приложения, поэтому пропущенные во время простоя даты догоняются. Для каждой даты транзакция, audit-запись и новое nextRunAt фиксируются атомарно.

Планировщик запускается только в одном модуле и не допускает параллельное выполнение обработчика. Уникальный индекс по правилу и дате обеспечивает идемпотентность даже после повторного запуска.

### 7.5. Dashboard

GET /dashboard?months=6 возвращает данные в основной валюте пользователя:

- общие доходы, расходы и баланс;
- расходы по категориям для круговой диаграммы;
- доходы и расходы по каждому из последних шести месяцев для линейного графика;
- пять категорий с наибольшими расходами.

Все агрегаты вычисляются в PostgreSQL из baseAmount. Frontend не выполняет финансовые вычисления и только форматирует готовые значения.

## 8. Frontend

### 8.1. Организация

- src/app/ — router, providers, MUI theme, authentication boundary;
- src/pages/ — композиция маршрутных страниц;
- src/features/feature/ — компоненты, hooks, схемы Zod и преобразования конкретной функции;
- src/shared/api/ — HTTP-клиент, обработка cookie и ошибок, типы из OpenAPI;
- src/shared/ui/ — действительно переиспользуемые компоненты;
- src/shared/lib/ — независимые утилиты форматирования дат и денег.

Типы клиента генерируются из /api/docs-json, например с помощью openapi-typescript. При изменении API DTO, Swagger и клиентские типы обновляются вместе.

### 8.2. Состояние и формы

TanStack Query управляет всем серверным состоянием. Query key содержит пользователя, фильтры, сортировку и пагинацию. Фильтры транзакций хранятся в URL, чтобы страницу можно было обновить или передать ссылкой без потери состояния.

AuthProvider при старте запрашивает `GET /auth/me`: ответ 401 означает анонимную сессию, а остальные ошибки показываются отдельно от формы входа. Защищённые маршруты не рендерят содержимое до завершения этой проверки. Все auth-запросы используют cookie через `credentials: include`; JWT недоступен JavaScript и не сохраняется в localStorage. После выхода frontend отменяет активные запросы, переводит auth-query в состояние без пользователя и очищает остальные query- и mutation-кэши.

React Hook Form и Zod выполняют клиентскую валидацию. Денежные значения остаются строками до прохождения валидируемой границы. После mutation инвалидируется минимальный набор затронутых query keys.

Каждый экран явно реализует состояния loading, error, empty и success. Серверные field errors сопоставляются полям формы, а неизвестные ошибки показываются как общий alert.

Экран категорий хранит строку поиска и страницу в URL, а список загружает через TanStack Query с ключом, содержащим пользователя, поиск и пагинацию. Создание и изменение выполняются в одной валидируемой форме; удаление требует отдельного подтверждения. После mutation обновляются только кэш категорий текущего пользователя и зависимые сводки dashboard и бюджетов. Сетка карточек меняет число колонок через MUI breakpoints; выбранный цвет служит фоном значка, для которого вычисляется контрастный цвет. Название и тип остаются текстом независимо от цвета. На mobile форма категории открывается полноэкранно.

Auth-формы отображаются как компактная карточка на desktop и как полноширинная поверхность на mobile. Цвета, типографика, фон и focus-visible индикаторы задаются MUI theme. Поля имеют видимые labels, пароль можно показать или скрыть доступной кнопкой, общий alert получает фокус, а первая ошибка валидации фокусирует соответствующее поле. Повторная отправка блокируется на время запроса.

### 8.3. Страницы

- регистрация и вход;
- dashboard;
- список и форма транзакций;
- категории;
- месячные бюджеты;
- повторяющиеся транзакции;
- мастер CSV-импорта;
- журнал изменений.

### 8.4. Адаптивность и доступность

Интерфейс строится mobile-first на MUI theme и breakpoints. Таблицы на узком экране заменяются карточками. Диалоги имеют заголовок, управляемый фокус, клавиатурное управление и подтверждение удаления.

Графики Recharts используют responsive container, доступные подписи, легенды и tooltips. Рядом с каждым графиком выводится текстовая сводка тех же данных. Все поля имеют связанный label и текст ошибки.

## 9. Seed-данные

Идемпотентный backend/prisma/seed.ts создаёт:

- ровно 2 независимых пользователя: «Личный» и «Семейный»;
- ровно 12 пользовательских категорий, распределённых между аккаунтами;
- ровно 3 месячных бюджета, распределённых между аккаунтами;
- не менее 200 транзакций за последние 6 календарных месяцев;
- несколько активных повторяющихся правил;
- соответствующие audit-записи для seeded транзакций и бюджетов.

Аккаунты не образуют общее пространство: каждый видит только собственные категории, транзакции, бюджеты, правила и журнал. Демонстрационные пароли документируются в README и хешируются seed-скриптом; JWT secret поступает только из окружения.

Отдельный integration-тест проверяет количество сущностей, шестимесячный диапазон дат и отсутствие пересечения владельцев.

## 10. Docker Compose

Compose содержит:

- postgres с volume и healthcheck;
- одноразовый db-init, выполняющий prisma migrate deploy и идемпотентный seed;
- backend, который запускается после успешного db-init и предоставляет healthcheck;
- frontend на Nginx, который запускается после готовности backend.

Таким образом, чистая установка полностью поднимается одной командой:

~~~sh
docker compose up
~~~

Для разработки допускаются отдельные команды npm, но они не заменяют обязательный Compose-сценарий.

## 11. Тестирование и доказательства

Планируется больше минимальных десяти тестов:

- Jest unit-тесты доменных расчётов, дат, валют и планировщика;
- Supertest integration-тесты каждого endpoint;
- Vitest и Testing Library для форм, списков, состояний и графиков;
- Playwright E2E для критических сценариев и desktop/mobile viewport.

Backend integration-тесты используют отдельную PostgreSQL test database. Каждый тест создаёт собственные данные или очищает их детерминированно.

Auth-набор Supertest проверяет регистрацию, конфликт нормализованного email, неверные credentials, cookie flags, logout, 401 и блокировку базовой валюты. Testing Library проверяет клиентскую валидацию, серверные ошибки, pending-состояние и навигацию после входа. Playwright поднимает полный Docker Compose, входит обоими seed-аккаунтами и подтверждает недоступность защищённого маршрута после logout.

Обязательные сценарии:

- валидация CRUD на frontend и backend;
- 401 без JWT и 404 при попытке доступа к чужой записи;
- комбинированные фильтры, поиск, сортировка и пагинация;
- совпадение фильтров списка и CSV-экспорта;
- полный откат невалидного CSV-импорта;
- расчёт бюджетов и dashboard в основной валюте;
- отсутствие дублей повторяющихся транзакций;
- audit before/after и откат при ошибке аудита;
- seed-счётчики и диапазон шести месяцев;
- loading, error, empty и success состояния UI;
- desktop и mobile представления.

## 12. CI

GitHub Actions выполняет на pull request и push:

1. npm ci;
2. npm run lint;
3. npm run typecheck;
4. npm run test с PostgreSQL service container;
5. npm run build;
6. docker compose config;
7. сборку Docker-образов и короткий E2E smoke job при наличии достаточного времени CI.

Проверки не должны считаться успешными, если тестовый раннер не обнаружил ожидаемые тесты.

## 14. План разработки

Детальная последовательность работ, зависимости и критерии завершения вынесены в [детализированный план реализации](./docs/IMPLEMENTATION_PLAN.md).

1. Создать npm workspaces, строгие TypeScript-конфигурации, ESLint, Prettier и базовые CI checks.
2. Поднять NestJS, React/Vite и PostgreSQL; добавить Dockerfiles, Compose и healthchecks.
3. Спроектировать Prisma schema, создать первую миграцию и идемпотентный seed.
4. Реализовать JWT-аутентификацию и доказать изоляцию двух пользователей.
5. Через TDD реализовать категории и транзакции, затем фильтры, поиск и пагинацию.
6. Добавить атомарный аудит транзакций и бюджетов.
7. Реализовать бюджеты и dashboard с проверенными агрегатами.
8. Реализовать CSV mapping, атомарный импорт и согласованный экспорт.
9. Реализовать повторяющиеся транзакции, catch-up и защиту от дублей.
10. Завершить responsive UI, accessibility и E2E-сценарии.
11. Проверить чистый docker compose up, Swagger, seed и CI; актуализировать README и этот документ.

Архитектура должна обновляться в том же коммите, в котором меняется соответствующее архитектурное решение.
