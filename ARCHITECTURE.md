# Архитектура Taler

## 1. Назначение документа

Taler — full-stack приложение для учёта личных финансов. Этот документ фиксирует архитектуру и план разработки до начала реализации. Он основан на требованиях из [project_fullstack_app.md](./project_fullstack_app.md), выбранном стеке из [docs/TECH_STACK.md](./docs/TECH_STACK.md) и правилах из [AGENTS.md](./AGENTS.md).

Цель архитектуры — выполнить каждое требование буквально и обеспечить проверяемое доказательство его выполнения через REST API, интерфейс, автоматические тесты, seed-данные, Swagger, Docker Compose и CI.

## 2. Архитектурный стиль

Приложение строится как модульный монолит из трёх основных сервисов:

- React SPA, собираемый Vite и раздаваемый Nginx;
- NestJS REST API с планировщиком фоновых задач;
- PostgreSQL с доступом через Prisma ORM.

Микросервисы, Redis и очередь сообщений не используются: они не требуются для одного демонстрационного экземпляра приложения и увеличили бы стоимость разработки без доказуемой пользы.

~~~mermaid
flowchart LR
    U[Пользователь] -->|HTTPS / HTTP| F[React SPA / Nginx]
    F -->|/api/v1| B[NestJS REST API]
    F -->|/api/docs| S[Swagger UI]
    B --> P[Prisma Client]
    P --> D[(PostgreSQL)]
    J[NestJS Scheduler] --> B
~~~

В Docker Compose Nginx проксирует /api в backend. Это даёт одинаковый origin для frontend и API, упрощает cookie-аутентификацию и устраняет различия между локальным демо и production-подобным запуском.

## 4. Backend

### 4.1. Модули NestJS

- **AuthModule** — регистрация, вход, выход, выпуск и проверка JWT.
- **UsersModule** — профиль, основная валюта и часовой пояс.
- **CategoriesModule** — CRUD и поиск категорий.
- **TransactionsModule** — CRUD, поиск, фильтры и пагинация транзакций.
- **BudgetsModule** — месячные лимиты и расчёт прогресса.
- **RecurringTransactionsModule** — CRUD шаблонов и автосоздание операций.
- **DashboardModule** — агрегаты для статистики и графиков.
- **CsvModule** — атомарный импорт и потоковый экспорт CSV.
- **AuditModule** — неизменяемый журнал операций над транзакциями и бюджетами.
- **PrismaModule** — единственная точка создания и предоставления Prisma Client.
- **HealthModule** — healthcheck для Docker и smoke-проверок.

Контроллеры отвечают только за HTTP-контракт. DTO и pipes выполняют валидацию, сервисы содержат бизнес-правила, Prisma отвечает за сохранение данных. Prisma-модели напрямую через API не возвращаются.

### 4.2. Общие правила API

- Базовый префикс: /api/v1.
- URL ресурсов используют множественное число и kebab-case.
- Создание возвращает 201, чтение и изменение — 200, удаление без тела — 204.
- Некорректный ввод возвращает 400, отсутствие аутентификации — 401, конфликт состояния — 409.
- Отсутствующая и принадлежащая другому пользователю запись возвращает одинаковый 404.
- Неизвестные поля DTO отклоняются глобальным ValidationPipe.
- Денежные значения и курсы передаются строками, валюты — кодами ISO 4217 в верхнем регистре.
- Временные метки передаются в ISO 8601 UTC; финансовая дата — YYYY-MM-DD в часовом поясе пользователя.

Единая форма ошибки:

~~~json
{
  "statusCode": 400,
  "code": "VALIDATION_ERROR",
  "message": "Request validation failed",
  "details": []
}
~~~

Коллекции возвращаются в единой оболочке:

~~~json
{
  "items": [],
  "meta": {
    "page": 1,
    "pageSize": 20,
    "total": 0,
    "totalPages": 0
  }
}
~~~

page и pageSize должны быть положительными; максимальный pageSize равен 100. Сортировка транзакций по умолчанию — transactionDate DESC, id DESC, что обеспечивает детерминированную пагинацию.

### 4.3. Основные маршруты

| Группа | Маршруты и назначение |
|---|---|
| Auth | POST /auth/register, POST /auth/login, POST /auth/logout, GET /auth/me |
| Users | PATCH /users/me для валюты и часового пояса с доменными ограничениями |
| Categories | CRUD /categories, поиск по имени через GET /categories?search= |
| Transactions | CRUD /transactions; список принимает поиск, фильтры, сортировку и пагинацию |
| CSV | POST /transaction-imports, GET /transactions/export |
| Budgets | CRUD /budgets; ответы списка содержат потрачено, процент и признак превышения |
| Recurring | CRUD /recurring-transactions |
| Dashboard | GET /dashboard?months=6 |
| Audit | GET /audit-log с фильтрами и пагинацией |
| Service | GET /health, Swagger UI /api/docs, OpenAPI JSON /api/docs-json |

Все маршруты, кроме регистрации, входа, healthcheck и Swagger UI, защищены JWT. Каждый новый или изменённый endpoint документируется в Swagger и покрывается Supertest-тестом.

AuthModule нормализует email до lowercase, хеширует пароль Argon2 и выпускает короткоживущий JWT с `sub` и `email`. Токен передаётся только через cookie `access_token` с `HttpOnly`, `SameSite=Strict`, `Path=/` и сроком жизни, совпадающим с JWT; в production добавляется `Secure`. JwtAuthGuard проверяет cookie и сохраняет в request только `id` и `email`, которые контроллеры получают через `@CurrentUser`.

Auth и Users никогда не возвращают Prisma-модель пользователя напрямую. Публичный UserResponseDto содержит только `id`, `email`, `displayName`, `baseCurrency`, `timeZone`, `createdAt` и `updatedAt`. PrismaService создаёт единственный типизированный Prisma Client для модулей приложения. Изменение `baseCurrency` выполняется только после проверки отсутствия транзакций и бюджетов пользователя и отклоняется целиком с `409 BASE_CURRENCY_LOCKED`, чтобы остальные поля того же PATCH не применились частично.

## 5. Модель данных

### 5.1. User

- id, email, passwordHash, displayName;
- baseCurrency — основная валюта пользователя;
- timeZone — IANA timezone;
- createdAt, updatedAt.

Email уникален и нормализуется. Пароль хешируется Argon2. Основную валюту можно выбрать при регистрации и изменить только до появления первой транзакции, бюджета или повторяющегося правила. После этого API возвращает 409 BASE_CURRENCY_LOCKED, поскольку изменение валюты сделало бы курсы неоднозначными. Изменение часового пояса атомарно переносит `nextRunAt` всех правил на полночь той же календарной даты в новом поясе.

### 5.2. Category

- id, userId, name, icon, color, type;
- createdAt, updatedAt;
- уникальность (userId, name).

Категория всегда принадлежит пользователю. GET /categories возвращает items и meta с page (по умолчанию 1), pageSize (по умолчанию 20, максимум 100), стабильной сортировкой по имени и id и необязательным поиском search по подстроке имени без учёта регистра. Имя обрезается по краям и уникально внутри пользователя без учёта регистра; это правило поддерживается уникальным индексом PostgreSQL по userId и lower(name). icon — имя Material icon в snake_case, color — шестизначный #RRGGBB, type — INCOME или EXPENSE. Публичный ответ не содержит userId. Отсутствующая или чужая категория возвращает 404. Удаление разрешено только для неиспользуемой категории; при наличии транзакций, бюджетов или повторяющихся правил возвращается 409 CATEGORY_IN_USE.

### 5.3. Transaction

- id, userId, categoryId;
- type: INCOME или EXPENSE;
- amount — исходная сумма NUMERIC;
- currency — валюта исходной суммы;
- exchangeRateToBase — ручной курс к основной валюте на момент записи или последнего изменения;
- baseAmount — зафиксированная сумма в основной валюте;
- transactionDate, description;
- recurringTransactionId и scheduledDate для созданных планировщиком операций;
- createdAt, updatedAt.

Курс определяется как количество единиц основной валюты за одну единицу валюты транзакции. Для операции в основной валюте курс обязан быть равен 1. Для другой валюты пользователь вводит положительный курс вручную. baseAmount рассчитывается backend, а не принимается от клиента.

REST-контракт /transactions: POST, GET списка и записи, PATCH, DELETE. Клиент передаёт amount и exchangeRateToBase десятичными строками, transactionDate как YYYY-MM-DD; пользователь и baseAmount определяются сервером. PATCH пересчитывает baseAmount при изменении суммы, валюты или курса. Категория должна принадлежать пользователю и иметь тот же type. Список поддерживает совместимые search, dateFrom/dateTo, categoryId, minAmount/maxAmount и type, сортируется по transactionDate DESC, id DESC и возвращает page/pageSize с общим количеством. Чужая запись неотличима от отсутствующей (404).

Индексы создаются по (userId, transactionDate, id) и (userId, categoryId, transactionDate). Уникальность (recurringTransactionId, scheduledDate) предотвращает повторное автосоздание одной операции.

### 5.4. Budget

- id, userId, categoryId;
- month — первый день месяца;
- limitAmount — лимит в основной валюте;
- createdAt, updatedAt;
- уникальность (userId, categoryId, month).

Прогресс не хранится: backend суммирует baseAmount расходных транзакций нужной категории за месяц. Ответ включает spentAmount, remainingAmount, progressPercent и isExceeded.

REST-контракт /budgets: POST, GET списка и записи, PATCH, DELETE. Месяц передаётся как первый день `YYYY-MM-01`; если фильтр списка `month` опущен, используется текущий месяц в IANA-часовом поясе пользователя. `transactionDate` — календарная дата без времени, поэтому расходы выбираются в полуоткрытом диапазоне дат `[month, nextMonth)` без преобразования даты через UTC-смещение. Список сортируется по categoryId и id, поддерживает page/pageSize и возвращает items/meta.

Лимит задаётся положительной десятичной строкой с точностью до четырёх знаков исключительно в основной валюте профиля; клиент не задаёт валюту и userId. Ответ добавляет код основной валюты, `spentAmount` и `remainingAmount` как десятичные строки (остаток может быть отрицательным), `progressPercent` как число с округлением до двух знаков и `isExceeded` при строгом превышении лимита. В расчёт включаются только расходные транзакции владельца и категории по `baseAmount`, без хранения производных значений.

Создание и изменение бюджета разрешены только для расходной категории владельца; пока бюджет существует, тип этой категории нельзя сменить на доходный. Совпадение `(userId, categoryId, month)` отклоняется с 409; чужой бюджет или категория неотличимы от отсутствующих (404). CREATE, UPDATE и DELETE сохраняют снимки бизнес-полей бюджета в AuditLog в той же Prisma-транзакции, что и изменение бюджета.

### 5.5. RecurringTransaction

- id, userId, categoryId;
- тип, сумма, валюта, текущий ручной курс и описание шаблона;
- dayOfMonth, startDate, необязательная endDate;
- nextRunAt, isActive, createdAt, updatedAt.

Для дней 29–31 в коротком месяце используется последний календарный день. Пользователь может обновить ручной курс правила до следующего запуска; при создании операции актуальное значение правила копируется в транзакцию.

### 5.6. AuditLog

- id, userId, entityType, entityId, action;
- before и after в PostgreSQL JSONB;
- createdAt.

Журнал поддерживает только чтение. entityId хранится без обязательного внешнего ключа, чтобы запись сохранялась после удаления сущности. Снимки содержат только бизнес-поля, а денежные значения сериализуются строками. Пароли, JWT и другие секреты никогда не попадают в журнал.

AuditService получает `Prisma.TransactionClient` от вызывающего сервиса при записи AuditLog и использует только этот клиент. Сервис не открывает собственную транзакцию: вызывающая операция отвечает за общий commit или rollback изменения сущности и записи аудита. Вход записи не позволяет задавать `id` и `createdAt`, которые назначает база данных.

CRUD транзакций выполняет изменение и запись аудита в одном interactive Prisma transaction. CREATE сохраняет только after, UPDATE — before и after, DELETE — только before. Снимки транзакций и бюджетов строятся из явного списка бизнес-полей: Decimal превращается в десятичные строки, даты — в ISO, userId, timestamps модели, пароль и другие служебные или секретные поля не копируются. Для бюджетов та же схема подключается при реализации CRUD в разделе 9.

GET /audit-log доступен только аутентифицированному владельцу, поддерживает совместимые фильтры entityType, action, dateFrom/dateTo (календарные дни UTC включительно) и page/pageSize. Сортировка — createdAt DESC, id DESC; ответ содержит items и meta. Из HTTP-интерфейса журнала не предоставляются операции изменения или удаления.

Frontend-маршрут /audit-log хранит фильтры и страницу в URL, запрашивает только записи текущего пользователя через TanStack Query и показывает таблицу на широком экране и карточки на узком. Диалог деталей сравнивает именованные бизнес-поля снимков before/after; для транзакции перед ссылкой на её просмотр проверяется существование через защищённый GET /transactions/:id. Если запись уже удалена, ссылка не отображается. Для бюджетов ссылка появится вместе с экраном их просмотра в разделе 9.

После создания, изменения или удаления транзакции frontend инвалидирует кеш журнала текущего пользователя, чтобы ранее открытая страница не показывала устаревшие записи.

В деталях аудита изменённые поля получают текстовые статусы вместе с цветовым акцентом, чтобы различие было понятно без восприятия цвета. Узкий экран показывает записи в семантической хронологии карточек; кнопки деталей и диалог доступны с клавиатуры. Временные метки отображают дату и время в IANA-часовом поясе профиля, причём исходный ISO timestamp сохраняется в атрибуте `dateTime`.

## 6. Безопасность и изоляция данных

JWT хранится в cookie с флагами HttpOnly и SameSite=Strict; в production также устанавливается Secure. Frontend не получает доступ к содержимому токена. Swagger UI работает через тот же origin и после вызова endpoint входа может выполнять защищённые запросы.

Идентификатор пользователя берётся только из проверенного JWT. Backend не принимает userId владельца в защищённых request DTO. Каждая операция Prisma ограничивается текущим userId, а ссылки на категории, бюджеты и повторяющиеся правила дополнительно проверяются на принадлежность тому же пользователю.

Для CORS разрешается только явно настроенный origin. Обязательные переменные окружения валидируются при старте. .env не коммитится; актуальный .env.example содержит только имена и безопасные примеры.

## 7. Ключевые бизнес-процессы

### 7.1. Аудит

Создание, изменение или удаление транзакции либо бюджета и соответствующая запись AuditLog выполняются в одной Prisma-транзакции. При ошибке откатываются обе операции. Аудит создаётся также для транзакций, добавленных через CSV и планировщик.

### 7.2. CSV-импорт

POST /transaction-imports принимает multipart/form-data с полями `file` (CSV) и `mapping` (JSON-объект: ключи `date`, `amount`, `category`, `type`, опционально `description`, `currency`, `rate`; значения — имена колонок). Повторное использование одной колонки и отсутствие обязательного сопоставления недопустимы. Заголовки должны быть непустыми и уникальными. Категория в строке задаётся её именем или UUID, но разрешается только среди категорий текущего пользователя с соответствующим типом. Отсутствующая валюта означает основную валюту пользователя, для неё курс всегда равен 1; для иной валюты обязательны отдельные колонки валюты и курса. Сервер принимает только UTF-8 (допускается BOM) и MIME `text/csv`, `application/csv` или `application/vnd.ms-excel`; пределы размера и числа строк задают `CSV_MAX_FILE_SIZE_BYTES` и `CSV_MAX_ROWS`.

При ошибках разбора или проверки ответ 400 содержит `code` и `details` с номером строки, полем и причиной. Ни одна операция при этом не сохраняется. После полной проверки строки создаются вместе с audit CREATE-записями в одной Prisma-транзакции; ответ 201 содержит число импортированных строк.

1. Papa Parse читает заголовки и несколько строк на frontend.
2. Пользователь сопоставляет колонки с датой, суммой, категорией, описанием, типом, валютой и курсом.
3. Frontend отправляет исходный файл и JSON-маппинг как multipart/form-data.
4. Backend заново разбирает файл через csv-parse, проверяет каждую строку и принадлежность категорий.
5. Импорт атомарный: при любой ошибке ничего не записывается, а ответ содержит номера строк и причины.
6. При успехе транзакции и их audit-записи создаются в одной Prisma-транзакции.

Frontend-экран `/transaction-imports` ведёт пользователя через выбор исходного файла, сопоставление колонок, предварительный просмотр и результат. Текущий этап обозначен доступным текстовым stepper; на узком экране сопоставление остаётся вертикальной формой. Область загрузки активируется клавиатурой и дополнена обычной кнопкой выбора файла. Ошибки строк выводятся списком с переходом к началу блока. Papa Parse читает только заголовки и образец строк для подсказок; результат просмотра не разрешает импорт и не заменяет серверную проверку. Выбранный файл и mapping сохраняются при возврате между шагами, в том числе после ошибок строк. После успешного импорта инвалидируются пользовательские запросы транзакций, dashboard, бюджетов и аудита.

Размер файла и количество строк ограничиваются конфигурацией. Для операции не в основной валюте CSV обязан содержать валюту и курс; для основной валюты backend устанавливает курс 1.

### 7.3. CSV-экспорт

GET /transactions/export принимает те же фильтры, что и список транзакций: даты, категорию, диапазон суммы, тип и поиск по описанию. Пагинация не применяется. Ответ имеет Content-Type: text/csv и Content-Disposition: attachment; выгружаются только данные текущего пользователя.

Экспорт использует общий builder фильтров и ту же сортировку (дата и id по убыванию). Колонки: `transactionDate`, `type`, `amount`, `currency`, `exchangeRateToBase`, `baseAmount`, `category`, `description`. Поля экранируются как CSV, а текст, начинающийся с потенциальной формулы (включая пробелы перед `=`, `+`, `-`, `@`), получает префикс-апостроф для защиты при открытии в электронных таблицах.

Кнопка экспорта на странице транзакций использует те же фильтры из URL, что и список, но не передаёт `page` и `pageSize`. CSV загружается через авторизованный API-клиент как файл; ошибки загрузки показываются на странице.

Проверки CSV разделены по границам: Supertest покрывает классы ошибок импорта, лимиты, изоляцию владельцев, атомарность и число audit-записей; интеграционные тесты с выделенной PostgreSQL проверяют сохранение и откат; Testing Library проверяет mapping, ошибки и состояния отправки; Playwright проходит импорт fixture-файла и экспорт отфильтрованного результата.

### 7.4. Повторяющиеся транзакции

Защищённые POST, GET списка/записи, PATCH и DELETE `/recurring-transactions` работают только с правилами владельца; список сортируется по `nextRunAt`, `id` и использует общую пагинацию. DTO валидируют день месяца (1–31), реальные календарные даты, `endDate >= startDate`, совпадение типа категории, положительную сумму и ручной курс. Для основной валюты курс равен 1. В ответе суммы и курс — десятичные строки, календарные даты — `YYYY-MM-DD`, `nextRunAt` — UTC timestamp. Правило можно приостановить через `PATCH isActive: false` без удаления.

`nextRunAt` — первый момент локальной календарной даты в IANA timezone владельца. Для дня 29–31 в коротком месяце используется последний день месяца; переходы DST учитываются при каждом следующем запуске. Один declarative cron job периодически выбирает активные правила с `nextRunAt <= now`. Обработчик также выполняется при старте приложения, поэтому пропущенные во время простоя даты догоняются. После `endDate` (включительно) правило деактивируется.

Планировщик запускается только в одном модуле и не допускает параллельное выполнение обработчика в рамках процесса. Условное обновление `nextRunAt` защищает от гонки между процессами. Для каждой даты создание Transaction, audit-запись и новое `nextRunAt` фиксируются одной Prisma-транзакцией. Уникальный индекс `(recurringTransactionId, scheduledDate)` обеспечивает идемпотентность: уже существующее occurrence продвигает расписание без новой операции и audit-записи.

Frontend-маршрут `/recurring-transactions` доступен после входа. Страница получает правила через TanStack Query с ключом пользователя и страницы, категории — отдельным запросом. `RecurringRuleList` показывает компактную таблицу при ширине `lg` и выше, карточки — на узких и средних экранах; неактуальное представление не монтируется. Оба представления показывают расписание, дату следующего запуска в часовом поясе пользователя, активность с текстом и доступной иконкой, сумму и курс. Безопасные действия редактирования и паузы визуально и семантически отделены от удаления; форма и подтверждение удаления вынесены в отдельные диалоги. POST/PATCH/DELETE инвалидируют список правил, а pause/resume выполняется через PATCH `isActive`. Для неосновной валюты интерфейс предупреждает, что курс хранится в правиле и обновляется вручную.

### 7.5. Dashboard

Frontend-запрос dashboard кэшируется TanStack Query под ключом пользователя и числа месяцев. Страница преобразует десятичные строки API в числовые значения только для координат Recharts; текстовые суммы берёт из исходных строк. Карточки итогов, круговая диаграмма расходов, помесячная динамика, топ категорий и текстовая сводка получают подготовленные данные и показывают собственные пустые состояния независимо друг от друга. Мутации транзакций и бюджетов инвалидируют dashboard-запрос текущего пользователя; импорт CSV должен использовать тот же префикс ключа после появления экрана импорта.

Dashboard использует MUI grid: на узком экране виджеты идут одной колонкой, на desktop графики и текстовые блоки располагаются попарно. Карточки итогов занимают всю ширину сетки. Высота Recharts ограничена, а контейнеры допускают сжатие без горизонтального переполнения. Цвет категории дублируется текстовой легендой с названием и суммой; графики также имеют короткие подписи и доступную текстовую сводку со всеми категориями и месяцами. Tooltip остаётся внутри доступной ширины на mobile.

Доказательства dashboard разделены по границам: Supertest с выделенной PostgreSQL test DB проверяет десятичные суммы, шесть месяцев с нулями, top-5 и изоляцию владельцев; Testing Library проверяет loading, error, empty и доступные подписи; Playwright проверяет seed-данные в настоящем backend и desktop/mobile без переполнения и ошибок консоли. Локальный прогон seed-E2E использует только `taler_test`, поскольку штатный seed заменяет данные демонстрационных аккаунтов.

GET /dashboard?months=6 — защищённый read-only endpoint. `months` опционален, по умолчанию 6, допустимы целые значения от 1 до 12. Период включает текущий календарный месяц в IANA-часовом поясе пользователя и предыдущие `months - 1` месяцев; границы для `transactionDate` образуют полуоткрытый диапазон `[fromMonth, nextMonth)`. Все суммы относятся только к этому периоду и передаются десятичными строками с четырьмя знаками в основной валюте пользователя:

- общие доходы, расходы и баланс;
- расходы по категориям для круговой диаграммы;
- доходы и расходы по каждому месяцу периода для линейного графика, включая нулевые месяцы;
- пять категорий с наибольшими расходами.

Ответ содержит `currency`, `months`, `fromMonth`, `toMonth`, `totals` (`income`, `expense`, `balance`), `expensesByCategory`, `monthlySeries` и `topCategories`. В категориальных элементах возвращаются id, имя, цвет и сумма; категории без расходов опускаются. Категории сортируются по сумме расходов по убыванию, затем по имени и id по возрастанию; top-5 — первые пять элементов этого порядка. Баланс равен доходам минус расходам, в том числе может быть отрицательным. При отсутствии операций totals равны нулю, категориальные массивы пусты, а monthlySeries содержит все месяцы периода.

Prisma группирует по дате, типу и категории и суммирует сохранённый `baseAmount` в PostgreSQL с обязательным фильтром `userId`; сервис объединяет дневные группы по месяцам, заполняет пробелы и формирует представления без вычислений через JavaScript `number`. Метаданные категорий запрашиваются отдельно, также с фильтром `userId`. Frontend не выполняет финансовые вычисления и только форматирует готовые значения.

## 8. Frontend

### 8.1. Организация

- src/app/ — router, providers, MUI theme, authentication boundary;
- src/pages/ — композиция маршрутных страниц;
- src/features/feature/ — компоненты, hooks, схемы Zod и преобразования конкретной функции;
- src/shared/api/ — HTTP-клиент, обработка cookie и ошибок, типы из OpenAPI;
- src/shared/ui/ — действительно переиспользуемые компоненты;
- src/shared/lib/ — независимые утилиты форматирования дат и денег.

Типы клиента генерируются из /api/docs-json, например с помощью openapi-typescript. При изменении API DTO, Swagger и клиентские типы обновляются вместе.

### 8.2. Состояние и формы

TanStack Query управляет всем серверным состоянием. Query key содержит пользователя, фильтры, сортировку и пагинацию. Фильтры транзакций хранятся в URL, чтобы страницу можно было обновить или передать ссылкой без потери состояния.

AuthProvider при старте запрашивает `GET /auth/me`: ответ 401 означает анонимную сессию, а остальные ошибки показываются отдельно от формы входа. Защищённые маршруты не рендерят содержимое до завершения этой проверки. Все auth-запросы используют cookie через `credentials: include`; JWT недоступен JavaScript и не сохраняется в localStorage. После выхода frontend отменяет активные запросы, переводит auth-query в состояние без пользователя и очищает остальные query- и mutation-кэши.

React Hook Form и Zod выполняют клиентскую валидацию. Денежные значения остаются строками до прохождения валидируемой границы. После mutation инвалидируется минимальный набор затронутых query keys.

Каждый экран явно реализует состояния loading, error, empty и success. Серверные field errors сопоставляются полям формы, а неизвестные ошибки показываются как общий alert.

Экран категорий хранит строку поиска и страницу в URL, а список загружает через TanStack Query с ключом, содержащим пользователя, поиск и пагинацию. Создание и изменение выполняются в одной валидируемой форме; удаление требует отдельного подтверждения. После mutation обновляются только кэш категорий текущего пользователя и зависимые сводки dashboard и бюджетов. Сетка карточек меняет число колонок через MUI breakpoints; выбранный цвет служит фоном значка, для которого вычисляется контрастный цвет. Название и тип остаются текстом независимо от цвета. На mobile форма категории открывается полноэкранно.

Экран транзакций хранит поиск, все фильтры и страницу в URL; отдельная query-key factory включает пользователя и каждый параметр списка. Список запрашивается через типизированный API-клиент, категории загружаются для фильтра и формы отдельно. Таблица и карточки отображают одни и те же операции, а пагинация использует meta ответа. Создание и изменение выполняются в диалоге React Hook Form + Zod; курс показывается только для валюты, отличной от основной, а денежные значения остаются строками. Удаление требует подтверждения. После мутаций инвалидируются список транзакций пользователя и зависящие сводки.

Экран бюджетов хранит выбранный месяц и страницу в URL; при отсутствии месяца выбирает текущий календарный месяц в часовом поясе профиля. Данные /budgets и список расходных категорий загружаются отдельными TanStack Query-запросами с ключами пользователя и параметров. Карточки показывают лимит, расход, остаток и числовой прогресс, включая превышение и отсутствие расходов. Создание и изменение бюджета выполняются через одну форму React Hook Form + Zod с денежной строкой, удаление — через подтверждение. После сохранения бюджета для другого месяца экран переключается на этот месяц. Каждая мутация инвалидирует бюджеты, сводку dashboard и аудит текущего пользователя.

Сетка бюджетов использует одинаковую высоту карточек в строке: одна колонка на узком экране, две на tablet и три на desktop. Шкала прогресса визуально ограничена 100%, но рядом показывает фактический процент и текстовый статус; эти данные связаны с индикатором для скринридера. Превышение выделяется цветом `theme.palette.error` и текстом, поэтому состояние не зависит от восприятия цвета. Длинные проценты и суммы не должны расширять страницу по горизонтали.

Проверка бюджетов объединяет изолированные Supertest-сценарии CRUD, валидации, владения, месячных границ, валютных сумм и атомарного аудита с компонентными тестами выбора месяца и состояний progress. Сквозной Playwright-сценарий создаёт отдельную расходную категорию и бюджет, добавляет расход через интерфейс транзакций и проверяет обновлённый progress после возвращения на экран бюджетов; созданные данные удаляются в конце. Основной режим проверяет настоящий Compose-стек, быстрый UI-режим моделирует API без изменения базы данных.

Представление транзакций использует на desktop таблицу с закреплённой колонкой действий и выравниванием сумм, а на mobile — карточки без горизонтальной прокрутки. Тип операции обозначается доступной иконкой, текстом и знаком суммы. Категория и даты доступны как быстрые фильтры на любой ширине; остальные фильтры на mobile открываются в drawer, сохраняя URL-состояние. Денежные суммы форматируются через Intl с явной локалью `ru-RU`, а календарная дата `YYYY-MM-DD` — через Intl в UTC, чтобы часовой пояс браузера не сдвигал день.

Auth-формы отображаются как компактная карточка на desktop и как полноширинная поверхность на mobile. Цвета, типографика, фон и focus-visible индикаторы задаются MUI theme. Поля имеют видимые labels, пароль можно показать или скрыть доступной кнопкой, общий alert получает фокус, а первая ошибка валидации фокусирует соответствующее поле. Повторная отправка блокируется на время запроса.

## 9. Seed-данные

Идемпотентный backend/prisma/seed.ts создаёт:

- ровно 2 независимых пользователя: «Личный» и «Семейный»;
- ровно 12 пользовательских категорий, распределённых между аккаунтами;
- ровно 3 месячных бюджета, распределённых между аккаунтами;
- не менее 200 транзакций за последние 6 календарных месяцев;
- несколько активных повторяющихся правил;
- соответствующие audit-записи для seeded транзакций и бюджетов.

Аккаунты не образуют общее пространство: каждый видит только собственные категории, транзакции, бюджеты, правила и журнал. Демонстрационные пароли документируются в README и хешируются seed-скриптом; JWT secret поступает только из окружения.

Отдельный integration-тест проверяет количество сущностей, шестимесячный диапазон дат и отсутствие пересечения владельцев.

## 10. Docker Compose

Compose содержит:

- postgres с volume и healthcheck;
- одноразовый db-init, выполняющий prisma migrate deploy и идемпотентный seed;
- backend, который запускается после успешного db-init и предоставляет healthcheck;
- frontend на Nginx, который запускается после готовности backend.

Таким образом, чистая установка полностью поднимается одной командой:

~~~sh
docker compose up
~~~

Для разработки допускаются отдельные команды npm, но они не заменяют обязательный Compose-сценарий.

## 11. Тестирование и доказательства

Планируется больше минимальных десяти тестов:

- Jest unit-тесты доменных расчётов, дат, валют и планировщика;
- Supertest integration-тесты каждого endpoint;
- Vitest и Testing Library для форм, списков, состояний и графиков;
- Playwright E2E для критических сценариев и desktop/mobile viewport.

Backend integration-тесты используют отдельную PostgreSQL test database. Каждый тест создаёт собственные данные или очищает их детерминированно.

Auth-набор Supertest проверяет регистрацию, конфликт нормализованного email, неверные credentials, cookie flags, logout, 401 и блокировку базовой валюты. Testing Library проверяет клиентскую валидацию, серверные ошибки, pending-состояние и навигацию после входа. Playwright поднимает полный Docker Compose, входит обоими seed-аккаунтами и подтверждает недоступность защищённого маршрута после logout.

Для транзакций Supertest покрывает CRUD, Decimal, изоляцию, отдельные и комбинированные фильтры, включительные границы и пагинацию; Testing Library — URL-состояние, загрузку, ошибки, пустой/успешный список и исходы мутаций. Playwright повторяет создание, фильтрацию, изменение и удаление на desktop и mobile. Основной E2E-режим использует настоящий Compose-стек; быстрый `e2e:ui` запускает тот же браузерный сценарий с изолированными ответами API и не подменяет проверку backend/PostgreSQL.

Обязательные сценарии:

- валидация CRUD на frontend и backend;
- 401 без JWT и 404 при попытке доступа к чужой записи;
- комбинированные фильтры, поиск, сортировка и пагинация;
- совпадение фильтров списка и CSV-экспорта;
- полный откат невалидного CSV-импорта;
- расчёт бюджетов и dashboard в основной валюте;
- отсутствие дублей повторяющихся транзакций;
- audit before/after и откат при ошибке аудита;
- seed-счётчики и диапазон шести месяцев;
- loading, error, empty и success состояния UI;
- desktop и mobile представления.

## 14. План разработки

Детальная последовательность работ, зависимости и критерии завершения вынесены в [детализированный план реализации](./docs/IMPLEMENTATION_PLAN.md).

1. Создать npm workspaces, строгие TypeScript-конфигурации, ESLint, Prettier и базовые CI checks.
2. Поднять NestJS, React/Vite и PostgreSQL; добавить Dockerfiles, Compose и healthchecks.
3. Спроектировать Prisma schema, создать первую миграцию и идемпотентный seed.
4. Реализовать JWT-аутентификацию и доказать изоляцию двух пользователей.
5. Через TDD реализовать категории и транзакции, затем фильтры, поиск и пагинацию.
6. Добавить атомарный аудит транзакций и бюджетов.
7. Реализовать бюджеты и dashboard с проверенными агрегатами.
8. Реализовать CSV mapping, атомарный импорт и согласованный экспорт.
9. Реализовать повторяющиеся транзакции, catch-up и защиту от дублей.
10. Завершить responsive UI, accessibility и E2E-сценарии.
11. Проверить чистый docker compose up, Swagger, seed и CI; актуализировать README и этот документ.

Архитектура должна обновляться в том же коммите, в котором меняется соответствующее архитектурное решение.
